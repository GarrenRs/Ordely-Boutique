# Ordely — Complete Architectural Audit

**Repository:** `conversational-order-os` (pnpm workspace v11, TypeScript ~5.9, React 19)
**Date:** 2026-09-15 | Live origin: `https://ordely.vercel.app`

> This document is a read-only audit result. No code was modified during its production.

---

## 1. What the System Does

Ordely is a **closed SaaS platform ("Conversational Order OS")** for Arab merchants (primary market: Algeria) to receive, manage and confirm product orders through **single-product landing pages** that customers order from directly. Cash-on-delivery (COD) commercial model: an order is a product (from a landing page) + delivery zone + commune + delivery method. Money is collected at delivery; merchants confirm/ship/deliver/return through a dashboard.

V1 is deliberately scoped to: **Landing Pages, Orders, Confirmation, Customers, Daily Reports.** No AI, workflow builder, marketplace, inbox, or page builder.

## 3. Frontend Architecture

- **React 19 + Vite 7 SPA**, routing via `wouter` (no SSR — fully client-rendered).
- State/server data via **TanStack React Query** (`lib/api-client-react` generated hooks using a custom fetch wrapper that supports session cookies with `credentials:"include"`).
- **shadcn/ui (Radix) + Tailwind 4** component library. framer-motion, recharts (reports), react-hook-form + zod, sonner toasts, lucide icons, RTL-friendly.
- Route shell `src/App.tsx`:
  - `/provider/apply` — public merchant application
  - `/provider(...)` — provider admin (own auth context `ProviderAuthContext`)
  - `/s/:storeSlug/p/:productSlug`, `/s/:storeSlug`, `/p/:slug` — public storefront
  - everything else → merchant router (`AuthContext`), `/login`, dashboard.
- Panels: merchant dashboard (sidebar in `Layout.tsx`) and provider dashboard (`ProviderLayout.tsx`).

**Ordering of route matching matters** — `/provider/apply` is declared *before* `/provider/:rest*`, and public `/s`, `/p` routes are declared before the merchant catch-all.

## 4. Backend/API Architecture

- **Express 5** (`apps/api-server/src/app.ts`), served two ways:
  1. Standalone Node server (`dist/index.mjs`, dev/self-host).
  2. **Vercel Function**: `api/index.js` imports `apps/api-server/dist/app.mjs`. `vercel.json` rewrites `/api/:path*` → `/api?__path=:path*`; the handler reconstructs `req.url` to `/api/<path>` for Express.
- Middleware chain: pino-http logging → CORS (origin allow-list enforced only in production) → static `/uploads` (dev only) → JSON/urlencoded (8mb limit) → **express-session with connect-pg-simple store** in `order_os.sessions` (memory store in dev) → routers → 404 → error handler.
- Sessions: `order_os.sid` cookie, httpOnly, sameSite lax, secure in prod, 7-day maxAge. Session data: `userId/storeId/email/storeName` (merchant) or `providerUserId/providerEmail/providerName` (provider).
- Router mounting (`routes/index.ts`): health, `/auth`, `/public`, `/provider` unauthenticated where appropriate; all merchant data routes are namespaced `/stores/:storeId/...` and gated by `requireStoreAccess` (401 if no session, 403 if `storeId` mismatch). Rate limiting on login (10/15min) and public orders (20/hr).
- API contract is **OpenAPI 3.1** (`openapi.yaml`) → Orval generates both client hooks and Zod validators consumed server-side.
- Error handling is manual (status+JSON); orders/list does in-memory filtering after full-table select (no SQL pagination).

## 5. Database Schema & Relations

All tables live in a dedicated PostgreSQL schema **`order_os`** (Drizzle `pgSchema`). Managed by Drizzle Kit push + raw migration/ensure scripts (no SQL migration files — `drizzle-kit push` against live DB).

**Tables (schema `order_os`):**

|---|---|---|
| `stores` | id, name, **slug (unique)**, owner_name, phone, city, logo_url, is_active, subscription_plan_days, subscription_expires_at, timestamps | parent of everything |
| `users` | id, store_id, email (unique), password_hash | N:1 → stores |
| `provider_users` | id, name, email (unique), password_hash | standalone admin |
| `landing_pages` | id, store_id, category_id, product_name, price, description, image_url, product_images (jsonb), available_sizes/colors (jsonb), gallery_display, theme_color, template, slug, transport_mode, delivery_info, whatsapp_number, is_active | N:1 → stores; N:1 → product_categories (nullable) |
| `product_categories` | id, store_id, name, slug, is_default (partial unique per store), is_active, sort_order | N:1 → stores |
| `delivery_zones` | id, store_id, wilaya_code, wilaya_name, home_fee, office_fee, return_fee, is_active | N:1 → stores; 1 per store+wilaya |
| `delivery_commune_settings` | id, store_id, wilaya_code, commune_name, daira_name, is_active | N:1 → stores; 1 per store+wilaya+commune |
| `customers` | id, store_id, name, phone, city, notes | N:1 → stores; unique store+phone |
| `orders` | id, store_id, landing_page_id, product_image_url, customer_id, customer_name/phone/city/address, delivery_zone_id, delivery_wilaya_code/name, delivery_commune_name/daira_name, delivery_method (HOME/OFFICE), delivery_fee, return_fee, selected_size/color, quantity, unit_price, total_price, **status**, notes, confirmed_at/shipped_at/delivered_at/returned_at | N:1 stores, landing_pages, customers, delivery_zones |

**Notable schema gaps:** no FK on `audit_logs.order_id` cascade behavior noted; order addresses are denormalized snapshots (good practice — retains history if landing page is edited). `landing_pages.slug` unique per store; a **legacy routing** `/p/:slug` exists for products whose slug collides across stores (returns 409).

## 6. Authentication Systems

Two fully independent session-based auth flows (no JWT, no Supabase Auth — custom session cookie):

**Merchant auth** (`routes/auth.ts`):
- `POST /api/auth/login` — bcrypt compare against `users.password_hash`, rate-limited (10/15min); sets `userId/storeId/email/storeName` in session.
- `GET /api/auth/me` — session introspection.
- `PATCH /api/auth/password` — change password (session required).
- `POST /api/auth/logout`.

**Provider auth** (`routes/provider.ts`):
- `POST /api/provider/auth/login` — **dual-backend**: first checks env vars (`PROVIDER_EMAIL` + bcrypt-compare `PROVIDER_PASSWORD_HASH`, or plaintext `PROVIDER_PASSWORD` fallback), else checks the `provider_users` table. Sets provider fields in session.
- `GET /api/provider/auth/me`, `POST /api/provider/auth/logout`.

Both auth systems share the same cookie/session store — a logged-in merchant and provider can technically coexist in the same browser (separate session keys).

---

## 7. Provider Authentication (Admin)

Provider = super-admin platform operator. Env-based identity is **authoritative**; the `provider_users` table is a fallback only. Provider password comes from `.env` (`PROVIDER_PASSWORD_HASH`), merchant-accessible entry is through `/provider/login`.

Provider capabilities (all behind `requireProviderAuth`):
- `GET /provider/summary` — global KPIs (total/active stores — active = isActive AND subscription not expired; today's orders/confirmed/returned).
- `GET/POST /provider/stores`, `PATCH /provider/stores/:storeId` (edit fields, subscription plan days 30/180/365), `POST /provider/stores/:storeId/reset-password`.
- `POST /provider/leads`, `GET/PATCH /provider/leads/:leadId`, `POST /provider/leads/:leadId/convert`.
- `POST /provider/showcase/reseed` — reseeds demo store.

---

## 8. Merchant Authentication

Merchant = one store, one `users` row. Login via email+password. All data routes are mounted under `/api/stores/:storeId/...` and enforced by `requireStoreAccess` (checks `req.session.storeId === :storeId`). No self-serve signup — merchants are created by the provider (lead conversion or manual create). Seed default: `admin@store.com` / `admin123`.

---

## 9. Multi-Tenant Isolation

- **Store-scoped rows:** every business table carries `store_id`; composite unique keys (store_id, slug / phone / wilaya / commune) partition tenants.
- **API-level:** `requireStoreAccess` 403s mismatched `:storeId`; auth is session-based so a merchant only ever holds one store.
- **Public endpoints:** store resolved via slug with `isActive = true AND (subscription_expires_at IS NULL OR > now())` filter (`effectiveActiveStoreSql`) — expired/inactive stores are invisible publicly.
- **Weakness (see Security):** several merchant routes use `requireStoreAccess`, which is fine — but the `stores` router (`/api/stores/:storeId`) does its own in-route check too. The logged-in user's storeId comes from session; a store changed by provider mid-session leaves `session.storeName` stale. Also **no RLS** — isolation is entirely application-layer.

## 14. Orders Lifecycle

State machine (`lib/transitions.ts`) with audit logging:

```
NEW ──→ PENDING_CONFIRMATION ──→ CONFIRMED ──→ SHIPPED ──→ DELIVERED
          │  │                                                        ▲
          │  └──→ REJECTED                                          (terminal)
          └──→ CANCELLED
CONFIRMED ──→ CANCELLED      SHIPPED ──→ RETURNED (terminal)
```

- **Create:** public POST or merchant POST `/orders` → status `NEW`, snapshots product image/price, computes `total = price × qty`, delivery fee = officeFee (+ homeFee if HOME), returns fee; upserts customer by store+phone.
- **Confirm:** `POST /orders/:id/confirm` requires status `PENDING_CONFIRMATION` → sets `CONFIRMED` + `confirmed_at`.
- **Reject:** `POST /orders/:id/reject` from `PENDING_CONFIRMATION` → `REJECTED`.
- **Update:** `PATCH /orders/:id` merges fields, enforces valid transitions, sets stage timestamps, syncs customer row, audits.
- Metrics aggregate by status (`/orders/summary`, daily/weekly reports): revenue only counts DELIVERED; delivery revenue added; RETURNS subtract `return_fee` as loss.

**Note on flow:** orders are seeded as `NEW`; the confirmation panel shows only `PENDING_CONFIRMATION`. There is **no automatic NEW→PENDING_CONFIRMATION transition** — the merchant must move it, otherwise it stays NEW.

## 25. Potential Security Issues

**Critical:**
- **Live secrets committed** (root `.env`): real `DATABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SESSION_SECRET`, provider hash.
- **No RLS on Postgres** — if database access ever leaks (service key / connection string), all tenants' data exposed; `SUPABASE_SERVICE_ROLE_KEY` grants full database + storage control.
- **Provider login not rate-limited** (`providerRouter.post("/auth/login")` has no limiter though merchant login and public order do).
- **Session store mixing:** in dev (`SESSION_STORE != "postgres"`), memory store; deploy with multiple Vercel functions → sessions won't persist across instances unless `SESSION_STORE=postgres`. Production is correctly set, but a misconfig silently breaks auth.
- **Public order endpoint** accepts arbitrary `customerPhone` and auto-upserts customers; only 20/hr limit, no phone-format normalization or per-store abuse cap.

**Moderate:**
- `PATCH /auth/password` and `/stores/:storeId` route checks trust `req.session.storeId` which is set at login — stale after provider edits the store, and a merchant always sees all data of the store captured in session (correct, but implies a changed association leaks the old store).
- `ordersRouter` list/search & `confirmationsRouter` filter **in memory** after loading full table query — denial-of-service vector at scale; also `page/limit` always returned as `1`/length (no real pagination).
- Error handler returns generic 500 without leaking internals (good), but `app.ts` 404 handler and CORS both fine.
- `zod` imported differently across code (`zod` vs `zod/v4`) — validation drift risk.
- Unkeyed rate limiter uses default (IP) — behind Vercel proxy with `trust proxy:1`, relies on correct `x-forwarded-for`.

## 26. Potential Production Bugs

1. **Order list has no pagination** — will degrade with volume; also `page`/`limit` in response are placeholders.
2. **`formatOrder` spread of `Record<string, unknown>`** leaves unexpected DB columns untyped — relies on codegen alignment.
3. **`DELIVERED` revenue double-count risk** in reports if an order moves back (in practice status is terminal so fine).
4. **`weekly` report uses `new Date()` (server time) reducible only; `daily` uses `YYYY-MM-DD` input directly** — timezone consistency (Algeria UTC+1) not persisted.
5. `public.ts` `deliveryZonesForStore` returns only zones with `officeFee !== null`; a store wanting only HOME delivery (no officeFee) will show **zero** zones publicly — likely unintended.
6. `PATCH /orders/:id` allows editing `landingPageId`? Body schema (`UpdateOrderBody`) — if it permits `landingPageId`, product image/price snapshot may become inconsistent with the order's displayed product.
7. `createStoredImagePath` uses `folder` for logo (`"logo"`), product images don't pass a folder → both fine, but uploads from a stale `UPLOAD_DIR` path (`/uploads/stores/…`) don't map to Supabase URL structure on restore.
8. **Logout cookie bug:** login uses session name `order_os.sid`; logout clears cookie `connect.sid` (`auth.ts:52`) — **cookie is not cleared on logout**, server-side session destroyed but the client cookie persists (functional but sloppy, potential session-cookie-lifetime confusion).
9. `npm run build` runs `typecheck:libs` first across the whole monorepo — one bad lib breaks all builds.
10. Session secret is static in repo; rotation requires killing all sessions.

## 28. Data Recovery / Recreation Strategy

**What enables recovery:**
- Schema is entirely in Drizzle source (`lib/db/src/schema`) — can be recreated via `db:push` / `reset-schema` + scripts, but **data itself (orders/customers/landing pages) has no export/backup script**.
- `npm run db:reset` **destroys ALL production data** (`reset-order-os-schema.mjs` drops schema). Guarded but destructive.
- There is **no dump/backup, no snapshots, no export tooling** in-repo. Recovery = Supabase console (SQL editor / PITR / pg_dump) or manual scripts.

**Recreation plan (see sequence below):** re-provision schema (ensure-scripts) → recreate provider user from env → reseed via `seed-dev` / `create-tenant` / `provider:create` / showcase scripts → re-import images from Supabase bucket (URLs already stored on rows) → re-verify session table exists.

# Consolidated Summary

**What the system does:** closed multi-tenant SaaS for Algerian Arab merchants to publish product landing pages, collect COD orders, manage confirmation/shipping/delivery/returns, track customers, and see daily/weekly reports, run by a platform provider (admin) that signs up merchants via lead funnel and provisions 14-day trial stores with subscription plans. Deployed as Vite SPA + Express-on-Vercel-Function + Supabase Postgres/Storage.

## All Available Panels
- **Provider Admin** (`/provider`): Dashboard, Stores, Leads (convert-to-store), Reseed Showcase, Login.
- **Merchant Dashboard** (`/login` → `/`): Overview, Orders (+ Confirmations tab), Order Detail, Customers (+ detail), Landing Pages (list/form), Reports, Delivery System, Settings.
- **Public**: `/s/:storeSlug` storefront, `/s/:storeSlug/p/:productSlug` product, `/p/:slug` legacy, `/provider/apply` application, `/login`.

## All Available Routes (API)
- `/api/health`
- `/api/auth/login|logout|me|/password`
- `/api/provider/auth/login|logout|me`, `/api/provider/leads[:id][:/convert]`, `/api/provider/summary`, `/api/provider/stores[:storeId][/reset-password]`, `/api/provider/showcase/reseed`
- `/api/stores/:storeId/{landing-pages, product-categories, delivery-zones, orders, customers, confirmations, reports, uploads}`

  - uploads: `POST /product-image`, `POST /store-logo`

## All Database Entities
`stores`, `users`, `provider_users`, `product_categories`, `landing_pages`, `delivery_zones`, `delivery_commune_settings`, `customers`, `orders`, `audit_logs`, `merchant_leads`, `sessions` (all in schema `order_os`).

## User Roles
1. **Provider Admin** (env-based or `provider_users`) — platform operator.
2. **Merchant** (one per store) — dashboard operator.
3. **Public customer** — anonymous order placement via landing pages.

## Authentication Flow
Session-cookie (`order_os.sid`), Postgres-backed in prod. Merchant: login → session(userId, storeId) → `requireStoreAccess` guards all store routes. Provider: login → session(providerUserId) → `requireProviderAuth`; env-based identity wins over table.

## Store Creation Flow
Provider captures application via `/provider/apply` (→ lead) → provider reviews in `/provider/leads` → **Convert** (transaction: create `stores` with 14-day trial + `users` row with generated password + mark lead CONVERTED) → credentials shown once → merchant logs in. Alternate: manual create via provider stores UI or `tenant:create`/`provider:create` scripts.

## Order Lifecycle
NEW → PENDING_CONFIRMATION → CONFIRMED → SHIPPED → DELIVERED (terminal), with REJECTED (from pending), CANCELLED (from NEW or CONFIRMED), RETURNED (from SHIPPED). Every change is audited. Timestamps per stage.

## Public Customer Flow
Browse storefront `/s/:slug` → open product → select size/color + wilaya/commune + HOME/OFFICE + qty → POST order → success screen with payable total (`product + delivery`, COD). Customer auto-registered (store-scoped) on order.

## Deployment Architecture
Vercel: static SPA (`apps/web/dist/public`) + Serverless Function (`api/[...path].js`) importing esbuild-bundled Express (`apps/api-server/dist/app.mjs`), rewrites to SPA for non-API paths. Postgres via Supabase pooler; sessions in `order_os.sessions`; storage in Supabase bucket `product-images` via service role; CORS allow-list `ordely.vercel.app`.

## Environment Requirements
As listed in §22 — 9 mandatory env vars in prod plus optional `SUPABASE_STORAGE_PUBLIC_URL`, `PROVIDER_PASSWORD`, `PROVIDER_ID`, `UPLOAD_DIR`, `SHOWCASE_*`, `DEV_*`.

## Known Risks (top 5)
1. **Committed live secrets** — immediate rotation + gitignore enforcement.
2. **No RLS / full service-role key in function** — DB & storage exposed via env leak; prefer role-limited service key or RLS with JWT.
3. **`npm run db:reset` destroys production**; no backup/export scripts in-repo.
4. **No pagination + in-memory filtering** in orders/customers endpoints at scale.
5. **Session/cookie logout bug** (clears wrong cookie name) + unlimited provider login.

## Recommended Restoration Sequence
1. **Freeze** — do not run `db:reset` / `db:push-force` against live DB; snapshot current schema & data first (`pg_dump` schema + data; note Supabase bucket contents).
2. **Rotate secrets** — regenerate `SESSION_SECRET`, `DATABASE_URL` password, `SUPABASE_SERVICE_ROLE_KEY`; create `.env.example`; remove `.env` from git and add to `.gitignore`.
3. **Stand up local/dedicated env** — `pnpm install`, `npm run db:push` on a fresh Supabase (or local PG), then all `ensure-*` scripts in order (store-slugs → returned-status → delivery-system → delivery-communes → landing-page-store-slugs → landing-page-transport-mode → merchant-lead-conversion → order-product-images → sessions).
4. **Provision identities** — `provider:create` (or env provider), `tenant:create`/`db:seed` for base merchant, optionally `seed-showcase` for demo.
5. **Verify migrations against real prod snapshot** — replay the same `ensure-*` sequence on production after backing up, or diff schema via Drizzle.
6. **Restore data** from snapshot (tables in FK-safe order: stores → users → categories → landing_pages → delivery_zones → delivery_commune_settings → customers → orders → audit_logs → merchant_leads).
7. **Restore images**: table `image_url`/`product_images` are absolute Supabase URLs — re-upload only if objects were lost; validate bucket contents.
8. **Deploy** — set Vercel env vars, run `npm run vercel:build`, smoke-test login, one public order, confirm/reject, report, upload, and provider flow (`/provider`).
9. **Close gaps (recommended, not blocking restore):** add pagination, real logout cookie clear, provider-login rate limit, `.env.example`, backup script, and RLS + least-privilege Supabase key.
