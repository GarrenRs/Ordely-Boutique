## 1) السبب الجذري (Root cause)

السبب الجذري المغلق في هذه المرحلة: المعروض العمومي للمنتجات كان يقصره شرطان فقط - نشاط المتجر واشتراكه و `landing_pages.is_active`. كان المتجر يستطيع إخفاء منتج يدوياً (`is_active = false`) لكنه لم يملك أي مؤشر مبني على شرط التوصيل الفعلي، ما يعني أن منتجات قد تظهر عمومياً بينما المتجر لا يستطيع إنجاز أي توصيل (لا ولاية صالحة) أو أن بياناته ناقصة، مما يولّد طلبات غير قابلة للتنفيذ.

## 2) التنفيذ (Implementation)

تنفيذ قواعد الاستعداد المستمدة (derived readiness) عبر مكتبة مشتركة جديدة `apps/api-server/src/lib/readiness.ts`، وإعادة استخدامها في المسارات العمومية والتجارية دون أي عمود محفوظ أو مهمة خلفية (self-healing عند كل طلب). القاعدة الموافق عليها سابقاً:

- المتجر `is_active = true`
- اشتراك المتجر فعّال (`subscription_expires_at` فارغ أو مستقبلي)
- وجود ولاية توصيل واحدة صالحة على الأقل: `store_id` مطابق + `is_active` + `office_fee` غير فارغ + بلدية واحدة مفعّلة على الأقل (إعدادات البلديات)
- بيانات المنتج مكتملة (اسم، سعر > 0، وصف، slug)
- `landing_pages.is_active = true` (الإخفاء اليدوي يبقى صريحاً)

ترتيب أسباب استرداد عدم الجاهزية: `store_inactive` -> `subscription_expired` -> `no_usable_delivery_zone` -> `product_incomplete` -> `product_unpublished`.

## 3) الملفات المتغيّرة (Files changed)

- `apps/api-server/src/lib/readiness.ts` (جديد) - مكتبة مشتركة: مؤشرات الجاهزية، عدد الولايات الصالحة، أسباب الاسترداد، `effectiveActiveStoreSql` المعرَّف مرة واحدة.
- `apps/api-server/src/routes/public.ts` - إزالة نسخ SQL والولّيات المحلية، اعتماد الدوال المشتركة في: storefront `/s/:storeSlug` (ترشيح المنتجات بشرط جاهزية المتجر + اكتمال البيانات)، صفحة المنتج `/s/:storeSlug/p/:productSlug` (رفض غير-المنشور)، الرابط القديم `/p/:slug` (استبعاد متاجر غير جاهزة مع الحفاظ على قاعدة 404/409)، و`createPublicOrder` (حارس مبكر قبل أي إدراج يعيد go التوصيل 422 بنفس رسالة المسار وقبل إنشاء صف الطلب).
- `apps/api-server/src/routes/landing-pages.ts` - GET القائمة و GET المفرد يعيدان `publiclyLive` و `readinessReason`.
- `apps/api-server/src/routes/stores.ts` - GET قائمة المتاجر، GET المتجر، و PATCH يعيدون `deliveryReady`.
- `lib/api-zod/src/generated/api.ts` - إضافة `deliveryReady` إلى `GetStoreResponse`/`UpdateStoreResponse` و `publiclyLive`/`readinessReason` إلى `ListLandingPagesResponseItem`/`GetLandingPageResponse`.
- `lib/api-client-react/src/generated/api.schemas.ts` - إضافة الحقول نفسها إلى واجهتي `Store` و `LandingPage`.
- `lib/api-spec/openapi.yaml` - مواءمة مخططَي `Store` و `LandingPage`.
- `apps/web/src/pages/LandingPagesList.tsx` - شارة "منشور/غير منشور" (حسب `publiclyLive`) مع شريحة سبب الجاهزية بالعربية؛ لا تغيير تلقائي لـ `is_active`.
- `apps/web/src/pages/LandingPageForm.tsx` - تلميح أصفر مختصر عند غياب `deliveryReady`.
- `apps/api-server/src/tests/readiness.test.ts` (جديد) - اختبارات تكاملية.
- `apps/api-server/test-readiness.mjs` (جديد) + سكربت `test:readiness` في `package.json`.

## 4) المسند الشرطي / انتظام الحساب (Readiness predicate)

القاعدة المطبقة هي "استعداد مستنبط" لا "عمود مستمر". نقطة الصواب الوحيدة للجاهزية هي الحالة الحية في قاعدة البيانات وقت كل طلب. الفاصلة: كل مكتبة من "لا ولاية" تُحتَسب فقط عندما تكون الولاية فعّالة ولها `office_fee` وحيدة بلدية مفعّلة؛ إعدادات بلديات غير موجودة تعني "مفعّلة".

نسخ SQL الخاصة بصلاحية المتجر والاشتراك أصبحت في `readiness.ts` (`effectiveActiveStoreSql`) وأُعيد استخدامها في `public.ts` ولم تُترك مكررة.

## 5) سلوك العموم (Public behavior)

- `/api/public/s/:slug`: المتجر النشط ذو الاشتراك الفعّال يُحتفظ به، لكن المنتجات في الردّ تُصفّى بشرط جاهزية التوصيل واكتمال البيانات و `is_active`. متجر بلا ولاية صالحة => `products: []` (المتجر يظهر لكن بلا منتجات).
- `/api/public/s/:slug/p/:productSlug`: رفض `404 "المنتج غير متاح"` إن لم يكن المنتج منشوراً وجاهزاً.
- `/api/public/p/:slug` (قديم): استبعاد الصفحات التابعة لمتاجر غير جاهزة مع بقاء منطق 404/409 (التعدد) كما هو.
- `POST /api/public/.../order`: حارس قبل أي إدراج بصف أو زبون؛ عند فقدان جاهزية المتجر يعيد `422 "الولاية غير متاحة للتوصيل حاليا"` (نفس رسالة المسار القديم) وتظل قاعدة البيانات بلا أي صف طلب.
- لا تُكشف أسباب جاهزية التاجر للعموم إطلاقاً.

## 6) سلوك التجار (Merchant behavior)

- قائمة الصفحات وتفاصيلها: كل صفحة تحمل `publiclyLive` (منشور/غير منشور) و `readinessReason` (سبب مبدئي مطابق للقاعدة) دون أي تغيير تلقائي على `is_active`.
- بيانات المتجر (`/stores`, `/stores/:id`, PATCH): تحمل `deliveryReady`.
- رموز الأسباب المعتمدَة: `store_inactive`, `subscription_expired`, `no_usable_delivery_zone`, `product_incomplete`, `product_unpublished`.
- التسميات العربية في الواجهة: "المتجر غير مفعّل"، "اشتراك المتجر منتهي"، "أضف ولاية توصيل واحدة على الأقل بأسعار توصيل"، "المنتج مخفي يدوياً"، "بيانات المنتج غير مكتملة".
- لم تُفعَّل أي ميزات أخرى (انتهاء الصلاحية الكاملة P1-04، الإرجاع P1-03، التتبع P1-01، الإدخال اليدوي P2-01 خارج النطاق).

## 7) الاختبارات (Tests)

مواصفات محدثة: لا توجد بنية اختبارات سابقة في المستودع؛ فتم بناء اختبار تكاملي واحد `apps/api-server/src/tests/readiness.test.ts` يُجمَّع عبر esbuild (`test-readiness.mjs`) ويُشغَّل بـ `npm --prefix apps/api-server run test:readiness`. كل السيناريوهات داخل معاملة واحدة ترمي رمزاً خاصاً في النهاية لضمان تراجع كامل، ثم تُثبَت خلوّ القاعدة من أي أثر. النتيجة: 30 فحصاً جميعها نجحت، منها:

1. متجر بلا ولايات -> غير جاهز وسببه `no_usable_delivery_zone`.
2. ولاية غير مفعّلة -> لا تُحتسب.
3. ولاية بلا `office_fee` -> لا تُحتسب.
4. كل بلديات الولاية معطّلة -> لا تُحتسب.
5. ولاية واحدة صالحة -> جاهز و `publiclyLive = true`.
6. `is_active = false` يدوياً -> `product_unpublished`.
6b. سعر صفر -> `product_incomplete`.
7. استعادة التفاصيل -> جاهز بلا سبب.
8. اشتراك منتهي -> `subscription_expired`.
9. متجر معطّل -> `store_inactive`.
10. عزل عبر المتاجر: تهيئة B لا ترفع A والعكس صحيح.
10b. فقدان آخر ولاية -> الحارس يرفض، وbق صفّي طلب (أ = 0، ب = 0) صفريان.

## 8) نتائج التراجع (Regression)

تحقق تراجعي تشغيلي على الخادم المحدّث (منفذ 8080) مع متجر العرض الحقيقي `ordely-showcase` والمتاجر بلا جاهزية (`evaboutique`, `anaka-store`):

- storefront showcase -> 200 مع 8 منتجات كاملة ونشطة (لا حذف للمنتجات الجاهزة).
- storefront لمتجر بلا ولاية -> 200 مع `products: []`.
- صفحة منتج -> 200 مع ولايات التوصيل ورسومها كما كانت (رسوم 16/الجزائر = 450).
- رابط قديم `/p/sovage-pure` -> 200.
- تسجيل دخول التاجر -> دورة كاملة (قائمة المتاجر، تفاصيل المتجر، قائمة الصفحات وتفاصيلها) مع `deliveryReady`/`publiclyLive`/`readinessReason`.
- طلب عام حقيقي -> 201 ثم تنظيف كامل (أُزيل صف الطلب وسجلات التدقيق والزبون الجديد)، وعاد عدد الطلبات إلى ما كان.
- حجب الطلب عبر متجر غير جاهز -> لا منتجات -> لا طلب (مع عدم إنشاء صف).
- 30 فحصاً تراجعياً جميعها ناجحة.

## 10) سلامة قاعدة البيانات (Database integrity)

لا تغييرات مخطط (بدون أعمدة/جداول)، ولا ترحيل، ولا إعادة تغذية (seeding). بعد كل الاختبارات والتراجع التشغيلي أُعيد الفحص المباشر عبر SQL: متاجر الرمل = 0، إجمالي المتاجر = 3، الطلبات = 24، الزبائن = 15، الصفحات = 8، الولايات = 58، سجلات التدقيق = 74 - أي جميعها مطابق للخط الأساس قبل المرحلة. لم يُستدعَ `db:push` لعدم الحاجة إليه.

## 11) المخاطر المتبقية (Remaining risks)

- متجر النشط ذو الاشتراك الفعّال وولاية صالحة تبقى نقطة الوصول العمومية الوحيدة؛ إخفاء المنتج (`is_active=false`) يبقى إجراءً يدوياً ويعتمد وجاهة التاجر (متعمّد حسب النطاق).
- لا يُفْرض إنهاء صلاحية كاملة أو تجميد الدخول بعد (P1-04) - خارج نطاق هذه المرحلة.
- لا يوجد نظام تتبع طلبات عام أو فحص تلقائي لكل المتاجر في الخلفية؛ الجاهزية كاملة عند كل طلب فردي (تصميم "بدون وظيفة خلفية").
- أداء المسار القديم `/p/:slug` يفحص ولاية تخزين لكل متجر مطابق (عدد صغير) - مقبول حالياً.
- المتجر 3 والمتجر 4 في قاعدة التطوير لا يملكان ولاية صالحة ولا منتجات؛ لذلك لا تظهر لهما منتجات في الواجهة العمومية حالياً (سلوك متوقع وموثّق في القسم 5).
- يلاحظ أن `lib/api-zod` المولّد لا يزال ناقصاً حقول `subscriptionExpiresAt`/`subscriptionPlanDays` في استجابة المتجر (تناقض سابق خارج النطاق، نقطة تدوين لعملية إنعاش العقود لاحقاً).
